WHAT'S ACTUALLY WRONG (background for Eric — this matters, read it)
-------------------------------------------------------------------------------
I checked the live site's actual rendered CSS (not just the source code)
and found the real cause of "slides aren't the same size everywhere."

At some point, the code that turns each case-study page into a slide deck
was rewritten to directly reuse the Hero section's CSS classes
(`hero-slide`, `hero-rail`, `hero-canvas`, `hero-thumb`, etc.) instead of
having its own separate set. That's a reasonable thing to do — but it had
a side effect nobody caught: on a case-study page, each slide element now
carries BOTH its old class (`cs-section`) AND the new ones
(`presentation-slide hero-slide case-study-slide`) all on the exact same
element, not nested inside each other like the code elsewhere assumes.

That collision quietly breaks three things:

1. `.cs-section` still has a very old rule — `max-width:var(--measure)`,
   where `--measure` is 68 characters wide (meant for comfortable reading
   line-length in a normal scrolling page). That rule is still capping
   each slide at roughly 686px wide, while the Hero deck's slides render
   at up to 1136px wide. That's the actual, measured size difference I
   found between a Hero slide and a SecureID slide right now — not a
   rounding error, a real ~450px gap. This is the main fix.

2. Several CSS rules that were supposed to make case-study body text
   bigger (to match Hero's new, more readable body text) were written as
   `.presentation-slide .cs-section p` or `.case-study-deck
   .case-study-slide .cs-section p` — a "space" in a CSS selector means
   "this must be INSIDE that," i.e. a separate ancestor element
   containing a separate `.cs-section` descendant. But since all of those
   classes now live on the exact same single element, there is no such
   ancestor/descendant relationship anymore, so none of those rules
   actually match anything. I checked the real computed font size on the
   live page: case-study body paragraphs are rendering at 16px in the
   Inter font, not the 18px Raleway that was intended. This explains why
   the earlier body-text fix didn't visibly take.

3. Separately, on each case study's opening/cover slide, the small
   Role / Team / Scope / Tools row only sits underneath the text column,
   leaving the space under the project image empty. You asked for that
   row to stretch the full width of the slide, under both the image and
   the text, which needs a small change to the code that builds the
   cover slide, not just a CSS tweak.

This file fixes all three, with the corrected selectors that actually
match the current, real structure of the page — verified against the
live site's computed styles, not guessed from the source code alone.

PART A — fix the slide width/height bug (every slide becomes the same size)
-------------------------------------------------------------------------------

In assets/css/style.css, find this exact line:

    .cs-section li{ margin-bottom:8px; }

Immediately after it, add this new line:

    .cs-section.hero-slide{ max-width:none; margin:0; }

(This is a compound selector — no space between `.cs-section` and
`.hero-slide` — so it only applies to an element that has both classes at
once, which is exactly a case-study body slide. It cancels out the old
`max-width:var(--measure)` and `margin:0 0 56px` from the plain
`.cs-section` rule, letting the slide's actual size come from
`.hero-slide{ width:min(100%,1136px); height:min(100%,640px); }` instead
— the same rule that already sizes every Hero slide.)

Verify: load a case-study page (or describe the expected render) and
confirm each slide now visibly fills the same width as a Hero slide does
on the homepage, with no narrow, centered-looking panel anymore.
